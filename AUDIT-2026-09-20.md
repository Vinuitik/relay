## Part 1 — Why nothing works

Ranked by how much each one explains the symptoms you reported.

### 1. Sleep can never work: the feature is off by configuration on both machines

`POST /v1/suspend` returns `503` unless `RELAY_IDLE_SUSPEND_ENABLED=true` was set
when the runner started (`cmd/runnerd/main.go` only assigns `srv.Suspend` inside
`if idleCfg.Enabled`).

- Laptop: `runner/install/start-relay-runner.ps1` sets **only** `RELAY_LISTEN_ADDR`.
  The flag is never set → `srv.Suspend == nil` → every Sleep tap gets `503`.
- Server: `runner/install/runner.env.example` ships the flag **commented out**, and
  `install.sh` copies that file verbatim. Unless you hand-edited `/etc/relay/runner.env`,
  the server is in the same state.

Automatic idle-suspend is gated on the same flag, so the "suspends itself after
3 min idle" half has also never once run on either machine.

### 2. …and the phone never tells you it failed

`SuspendRunnerWorker` and `WakeRunnerWorker` are WorkManager jobs. Every failure
path — `401`, `403`, `503`, `409 busy`, connection refused, "wake not configured"
— ends in `Log.w(...)` + `Result.failure()`/`Result.retry()`. **Nothing is ever
surfaced to the UI.** The Sleep dialog shows "Suspending <host>…" unconditionally,
*before* the request is even attempted.

Result: a `503` and a success look identical on the phone. This is why both
buttons feel like they "do nothing" — they are in fact reporting failures, into
logcat, which you are not reading on a commute.

Contrast: every *screen* (`ChatScreen`, `ProjectListScreen`, `SessionListScreen`,
`FileBrowserScreen`) does route errors through `friendlyErrorMessage()` and shows
them. The two most important buttons in the app are the only paths that don't.

### 3. Linux suspend would still fail even with the flag on

`idle/shutdown_unix.go` runs `systemctl poweroff` **directly**, as the service
user, no `sudo`. `relay-runner.service` says in a comment:

> Give that user passwordless sudo for poweroff/shutdown specifically (see install.sh)

`install.sh` never creates any sudoers entry. And `shutdown_unix.go` never invokes
`sudo` anyway, so a sudoers entry wouldn't be used even if it existed. A systemd
service user with no active seat is normally denied `poweroff` by polkit
("Interactive authentication required"). So: doc says one thing, unit file says a
second, code does a third.

### 4. A session never becomes idle — so the runner is permanently "busy"

`session.StateIdle` is **declared and never assigned anywhere** (verified by grep;
the only hit is the constant's own definition). A session goes `busy` → and only
leaves `busy` when the subprocess *exits* or you explicitly Stop it.

But the claude provider is deliberately a long-lived process
(`claude --print --input-format=stream-json --output-format=stream-json --verbose`)
that stays alive across turns. So once you start one chat:

- `GET /v1/runner/info` reports `busy: true` forever.
- `POST /v1/suspend` returns **`409` — "cannot suspend while a session is busy"** forever.
- `idle.Monitor` never fires, forever.
- `OnFinished` never fires → **the job-done FCM push, the headline feature of the
  whole app, can never be sent for a claude session.** The only thing that fires it
  is you manually pressing Stop, which you'd only do after already seeing the answer.

The signal you need is already arriving and being thrown on the floor:
`decodeClaudeStreamJSONLine()` explicitly drops the stream-json `result` event,
which is exactly the per-turn "this turn is done" marker. Same for `busy`/`idle`
per turn.

This is the single deepest structural bug in the project. Idle-suspend, manual
suspend, and notifications are three separate features that all depend on a
busy→idle transition that does not exist.

### 5. Wake: the MAC in the QR code is the wrong NIC

`wol.LocalMAC()` picks "the first up, non-virtual interface with an IPv4 address".
On this laptop that resolves, deterministically, to:

- **WiFi** (ifIndex 12, `34-CF-F6-81-08-76`, 192.168.1.40/24) — because Ethernet
  (`CC-48-3A-32-F8-DD`, Intel I219-LM) is *Disconnected* and therefore skipped.

So the pairing QR embeds the **WiFi** MAC. Wake-on-WiFi (WoWLAN) is off by default
on essentially all consumer hardware, and a machine at S5 has its WiFi radio fully
powered down regardless. The Ethernet NIC — the only one that can actually be woken
— is the one the heuristic is guaranteed to skip whenever the cable is unplugged,
which is exactly when you're relying on WiFi.

The same applies to the server (`victor-aspire-a715-75g` is an Acer Aspire laptop).
**If either machine is woken over WiFi, WoL will never work at all**, independent of
every other bug in this report.

Related: `wol/localmac.go:15` tells you to "set `RELAY_WOL_MAC` manually instead".
`RELAY_WOL_MAC` **does not exist anywhere in the codebase**. There is no manual
override. The only escape hatch is typing the MAC into the app's Wake settings dialog.

### 6. Wake: the broadcast goes to an ambiguous interface

`udpSender.SendBroadcast` opens a socket on `0.0.0.0:0` and sends to the *limited*
broadcast address `255.255.255.255:9`. Which physical interface that egresses on is
decided by the OS routing table. This laptop currently has five interfaces with
IPv4 addresses up (WiFi, Tailscale, two Hyper-V vSwitches, plus link-local ones).
A magic packet is worthless if it leaves via `vEthernet (Default Switch)` or the
Tailscale tunnel.

The robust form is a *directed* broadcast (`192.168.1.255`) sent from a socket bound
to the LAN interface's own address — or simply sent once per non-virtual interface.
Neither is done.

### 7. Wake can't be configured while the target is off (chicken-and-egg)

`WakeViaMatcher.autoMatch` fills in `wakeViaRunnerId` by calling
`GET /v1/runner/info` on **both** runners and comparing `localSubnet`. The server has
been offline 17h. An offline runner returns nothing → no match → `wakeViaRunnerId`
stays null → tapping Wake shows *"Wake not configured"* and gives up.

So the only moment you can configure wake for a machine is while that machine is
already awake — and there's no retry, no persistence of the attempt, and no
re-match when it later comes back online. If you paired the server while it was
already down, wake for it was never configurable at all.

Also note the `localSubnet` matching was itself broken on Windows until commit
`f89a6e2` (three days ago) — it was reading the IPv6 link-local address and failing
its own IPv4 check.

### 8. Structural: there is no always-on relay device

The architecture requires a second always-on machine on the server's LAN to emit
the magic packet. You have two runners. The only candidate to wake the server is
this laptop — which is itself a machine you'd want asleep. So today the design is
circular: either the laptop never sleeps (defeating the premise), or nothing can
wake the server. The Pi Zero 2 W that resolves this hasn't been bought.

This isn't a bug, it's the known rollout-order gap — but it means "wake works"
cannot be demonstrated end-to-end right now no matter what you fix in code.

### 9. Laptop doesn't come back after a shutdown

`start-relay-runner.ps1`'s header claims the runner "comes back on its own after a
full shutdown/restart". It's a **logon**-triggered Scheduled Task. After S5, the
machine boots to the lock screen and the runner does not start until a human logs
in. So a woken laptop is a laptop you still can't reach. (`runner/FLOWS.md:385`
documents this correctly — the script's own comment is the one that lies.)

### 10. Self-update makes this worse on Windows, silently

`selfupdate` replaces the binary and **exits**, relying on systemd `Restart=always`.
On Windows there is no such restarter — the Scheduled Task only fires at logon. A
successful self-update on the laptop = the runner vanishes until next logon.

It also runs at startup and every 10 min, and a restart wipes **all** in-memory
state: every session transcript, every running agent subprocess, and every
registered FCM token.

### 11. Everything important is in-memory and lost on restart

- Sessions + transcripts: `session.Manager`, memory only.
- Registered FCM device tokens: `notify.Registry`, memory only.

The app only registers its FCM token in `MainActivity.onCreate`. So after any runner
restart, that runner can no longer notify your phone until you *open the app* —
which is precisely when you don't need a notification. Combined with #4, the
notification feature has approximately zero chance of ever firing in real use.

### 12. FCM is not actually wired on either machine

`RELAY_FCM_CREDENTIALS` is commented out in `runner.env.example` and never set by
`start-relay-runner.ps1`. `NewNotifier("")` returns `noopNotifier`, which logs
"FCM not configured, skipping notification" and returns nil. Meanwhile
`runner/install/fcm-service-account.json` sits in the repo, unreferenced by any
launcher. Even if #4 and #11 were fixed, no push would be sent.

### 13. Windows: `sh -c` doesn't exist

`sh` is not on PATH here (verified). That breaks:
- the `echo-agent` test provider (`sh -c cat`),
- **every** `RELAY_PROVIDER_*` env override, which `resolveProvider` implements as
  `sh -c <value>`.

So on Windows the *only* working provider path is bare PATH auto-detection. The
documented override mechanism is unusable on half your fleet.

### 14. The home-screen widget is probably dead

`RelayWidgetProvider` is declared `android:exported="false"`. An `AppWidgetProvider`
receives `ACTION_APPWIDGET_UPDATE` from the system AppWidgetService, i.e. from
outside the app — an unexported receiver won't get it. Additionally its Wake button
depends on a "widget default project" that has no visible configuration flow, so
even if it binds, `WakeRunnerWorker` bails at `Result.failure()`. (Medium confidence
— not tested on device.)

### 15. `AuthLoginScreen` doesn't exist

`RelayApiService.kt:64` references `[com.relay.app.ui.screens.AuthLoginScreen]`.
There's no such file. The route reuses `ChatScreen`, which is fine — the KDoc is
just stale. Harmless, but it's a symptom of how much of the doc surface is now
describing things that aren't there.

## Part 3 — Prune candidates

The project is ~5,800 lines with a large feature surface and a core loop that has
never once completed. Ranked by "cost to keep" vs "value before v1 works":

**Delete or disable now:**
1. **`internal/selfupdate` (264 lines) + `runner-release.yml`.** Actively harmful on
   Windows (#10), destroys in-memory state (#11), and you're hand-copying binaries
   anyway. This is auto-deployment for a thing that doesn't deploy yet.
2. **The widget** (`RelayWidgetProvider`, `StopContainersWorker`, `ContainersAllWorker`,
   `WidgetConfigRepository`, layout + xml). Likely non-functional (#14), and every
   action it offers already exists in `RunnerListScreen`.
3. **Firebase App Distribution in-app updater** (`MainActivity.checkForUpdate`). Adds a
   Custom Tab sign-in flow and an SDK dependency to solve a problem you don't have.
4. **`FriendlyNameGenerator`** — generating "Adjective Noun" defaults when you have
   two machines.

**Defer (keep the code, stop counting it as done):**
5. **Uptime + Dashboard + Room cache** (`internal/uptime`, `UptimeSyncWorker`,
   `DashboardScreen`, `data/db/*`). ~400 lines of analytics on a system with no
   working primary flow.
6. **`internal/history` + the hourly purge ticker.** Purging week-old sessions from a
   store that doesn't survive a process restart is dead weight.
7. **`/v1/containers/start-all` & `/stop-all`.** You have one registered project.
8. **`/v1/auth/login` pseudo-session.** Clever, but `claude` is already authenticated
   on this laptop, and it's a one-time-per-machine action you can do over SSH.

**Two ways to do one thing — pick one:**
9. `POST /v1/projects` with `name` (scaffold) vs with `path` (register existing), plus
   `GET /v1/browse` + `FolderPickerScreen`. Three entry points for "tell the runner
   about a directory".

Rough estimate: items 1–8 are ~1,500–1,800 lines of Go + Kotlin, none of which is
on the path to "wake the server from the train, ask Claude a question, get a push
when it's done".

## Part 4 — What I'd actually want decided

These are the forks where I don't want to guess:

1. **Is the server on Ethernet or WiFi?** If WiFi, Wake-on-LAN is dead as an approach
   and the whole S5 premise needs rethinking (e.g. S3 + WoWLAN, or a smart plug + BIOS
   "restore on power loss", or the Pi holding a GPIO on the power pins). This single
   fact decides whether findings #5/#6 are worth fixing at all.

2. **Busy/idle per turn, or per process?** Fixing #4 means treating the stream-json
   `result` event as end-of-turn: `busy` during a turn, `idle` between turns,
   `finished` only when the process exits. That changes what "a session" means
   (a long-lived conversation, not a job) and makes `finished` rare. It also means
   the notification fires per *turn*, not per session — which I think is what you
   actually want on a commute, but it's a product decision, not a bug fix.

3. **Do sessions need to survive a runner restart?** Today they don't, and the runner
   restarts itself every time self-update fires. If the answer is yes, that's a
   persistence layer (transcripts to disk) that doesn't exist yet. If no, then
   self-update has to go (#10) and the app needs to handle a 404'd session gracefully.

4. **Should the laptop be the wake relay, or should the Pi be bought now?** #8 says
   the current two-machine topology can't demonstrate wake at all. £16 removes an
   entire class of unfixable-in-code problems.

5. **Windows laptop: auto-logon or not?** Without it (#9), waking the laptop gives you
   an unreachable machine. The alternative is running the runner as a real Windows
   service, which self-update was explicitly designed around not doing.
